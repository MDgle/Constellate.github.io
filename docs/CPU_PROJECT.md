# Constellate CPU improvement project (started 2026-10-13)
Read this first in a new chat. Game file: constellate.html (build 2026-10-14-j = step 8 + Settings layout; -i after step 8; -h after step 7b; -g after step 7; -f after step 6; -e after step 5; -d after step 4; -c after step 3; started at -b). Harness: tools/harness.py.

## Goal
Hard CPU should judge a WHOLE TURN, not single moves. Objective: maximize points gained by end of round using all AP (unspent AP are worth nothing).
Opponent point loss is worth less than own point gain but still valuable; contesting a sector you can't flip is still valuable.
Score awareness: track leader gap and Deficit Elimination margin (last place >3 behind the player ahead = eliminated); if a leader is far ahead, catch them (steals swing both ways).
Known failure: a Hard CPU about to be eliminated spent its turn on 2 high-cost moves (+1 pt each) instead of several cheap gains/contests, and lost.

## Findings so far (from reading the code + baseline)
- cpuCands scores each candidate alone via cpuPot2 (own VP x10, plus ~0.4 per star of sector margin, clamped +-2); AP cost penalty is a flat 0.25/AP; steals are not range-limited (claims first try radius 3).
  A single sector-flipping steal (10) beats cheap moves worth ~0.4 each, even when 3 cheap moves together would flip more. Greedy marginal blindness is the cause.
- "Danger" (cpuDangerCheck) only turns off a center-sector discount; it does not change how AP are spent.
- Speed: ~90% of CPU time is cpuCands -> cpuPot2 -> calc (full-board scoring per candidate, ~33k calls/game, ~9 s per 4-Hard game in the sandbox; sandbox is 1 slow core). A turn planner needs INCREMENTAL scoring first.
- Baseline (build 2026-10-13-b), 2 players Hard vs Medium, 300 games, seats rotated: Hard wins 47.0% (+-5.6) = no better than Medium.
- Baseline style: 2p Hard and Medium both spend ~33% of AP on moves costing 4+, 15% of turns (AP>=6) use <=2 moves. 4p all-Hard (39 games): 51% of AP in 4+ cost moves, 19% of turns <=2 moves, 2.7 eliminations/game, ~17.8 rounds.

## Step 5 result (build 2026-10-14-e)
- Part 1, turn cache (levels 1-3 behavior IDENTICAL: 66 seeded games vs build -d, 0 differences): cclear(a,b) = remembered clear() computed by clearBB (bounding-box culling), dropped when the star count changes / G is replaced / a new CPU turn starts; cpuStrTab + cStr/cCs = one-pass strength table, only set inside read-only searches (cleared before any move and in cpuStep's finally); cpuBufTab/cpuBufFast = cpuBuffer without rebuilding the foe list per candidate. Speed (sandbox): 2p Hard vs Medium 30 games 11 s -> 7 s; 4p 6 games 7 s -> 5 s. harness --check now also compares clearBB vs clear and cpuBufFast vs cpuBuffer (0 mismatches).
- Part 2, planner (new "Turn planner" block before cpuStep; MAP comment updated): cpuPlanStep -> cpuPlanMake builds K=14 whole turns ("rollouts") on a lightweight copy of the board (cpuPlanInit/Clone/Gen/Apply, tally via incAdd), each by repeating "list all legal moves, value = incEval delta + old Hard bonuses with the retake discount, pick by value/cost^alpha" (alpha 0, 1, .5, 1.5, then random alpha + Gumbel noise) until the Actions are gone. A turn's value (leaf) = incEval of the final board + move bonuses - retake penalty (0.7 x loss for each own star an opponent could retake, +8 for a Capital) + look(0.5) x cpuPlanNext = a quick greedy rollout of MY NEXT turn (all stars rested, next round's Actions, opponents standing still). Best leaf is played through cpuDo; each move is re-checked on the real board (cpuPlanOK) and the plan is rebuilt if something no longer fits (max 6 plans per turn, then the old move-by-move code). apCost is not used by the planner. Fleets are still placed/moved BEFORE planning and not moved while a plan runs (step 6). Enabled for levels in cpuPlanLv = {4} (Hard+ test); harness --plan 3 adds level 3. cpuPlanCfg {K, ms (real-play time cap, ignored when cpuSeed set), thr, capPen, enable, look, maxPlans, pred, dbg}; cpuPS = counters.
- Simulation check (harness --planchk): after every fully executed plan the real sector counts and Actions left equal the planned ones: 1,298 plans exact, 0 mismatches (4 skipped because a move was stale); 218 earlier.
- KEY FINDING: without the next-turn lookahead the planner was NOT better (2p, 100 games, 4 vs 3: margin after round 6 -0.33, final +-0 +-5). Cause: many turns tie on this-turn board value (a 1-Action and a 2-Action claim into the same sector), so the planner ignored which leaves cheap points waiting for the next turn; old Hard's 0.25/AP penalty accidentally did that. The lookahead (look .5) fixed it. look 0.25 / 0.5 / 1.0 all gave 73-82% (within noise).
- A/B results, 2p, seats rotated: Hard+ (planner + step-4 terms) vs legacy Hard 78.7% (+-6.6), VP margin +14.3 (+-3.5), 150 games. Planner with the step-4 terms switched back to Hard's values (--set 4:oppVp=0 4:leaderBoost=0 4:marginOpp=0 4:elimPen=0) vs legacy Hard: 82.0% (+-7.5), margin +15.8 (+-4.3), 100 games => the planner is the gain; the step-4 terms are neutral so far (untuned). Hard+ vs Medium: 69.1% (+-7.8), margin +9.3 (+-4.2), 136 games (baseline Hard vs Medium was 47.0%).
- Style: Hard+ spends 20-24% of AP on 4+ cost moves (Hard 36-40%), 4.0 moves/turn vs 3.5, AP/move 2.4 vs 2.7.
- Speed: 30-60 ms per plan in the sandbox (14 rollouts, incl. lookahead), ~12-15 plans per 2p game; not yet timed on Android. Knobs if too slow: cpuPlanCfg.K, cpuPlanCfg.ms.
- Still weak/untested: (a) Hard+ is still slightly BEHIND at rounds 6-8 (-0.3 VP) and wins later; the early expansion phase could still be better. (b) 4p: only 8 mixed games run (too few to read). (c) defender Hold/Retreat randomness, where a new star lands inside a system, and defending Fleets are not modeled; no multi-step lookahead over opponent replies. (d) the "known failure" (about to be eliminated) has no scenario test yet (step 9).
- Harness additions: per-round VP snapshots (summary prints VP margin after rounds 4/6/8/10/12: much less noisy than the final margin), --plan LV, --pc KEY=VALUE (cpuPlanCfg), --planchk, planner stats line in the summary. tools/ also has cmp.py (seeded identity compare), prof.py (profiler), trace.py (move trace).

## Step 6 result (build 2026-10-14-f)
- RESULT: planning Fleets inside the turn is built and correct, but it did NOT make the CPU stronger than the current Fleet handling. Head-to-head, 2p, seats rotated, Hard+F (Fleets planned) vs Hard+ (Fleets placed/moved before the plan, as in build -e): 220 games, 50.0% (+-6.6) each, VP margin -0.25 (+-3.6), VP margin after round 10 +0.48 (+-0.31) for Hard+F (n=203, not significant). Decision: Hard+ (level 4) keeps the old Fleet code; the new code stays as the harness-only test level 5 (Hard+F), not in any menu. Do not spend more time on this unless a new idea appears (see 'Why' below).
- What was built (levels 1-4 byte-identical to build -e: seeded cmp.py 30 + 20 + 6 + 100 games, 0 differences): level 5 = level 4's values + `cpuFleetLv` {5} (levels that plan Fleets; `cpuFleetPlanOn()`). For those levels cpuStep starts with the plan instead of cpuPlace / cpuFleetMove. Inside cpuPlanMake: (1) cpuPlanPlace puts the Fleet pool on the copy one Fleet at a time (near enemy, protect a threatened star, or finish a capture the pool can complete), and rollouts 0-3 use four fixed styles (cpuPOL: balanced, attack-heavy+stacked, defence-heavy, balanced+stacked), later rollouts random weights, so the search picks the placement by the value of the whole turn; (2) 'fmove' = free move of n Fleets along own Connections (up to n), listed when it protects a star without exposing another (weight fmD); (3) 'ftake' = move Fleets, then take, as one move; (4) after the plan the old cpuFleetMove still tidies up (cpuPlanCfg.post). New cpuPlanCfg values: fPlace, fMove, fmA, fmD, ftake, post (documented above cpuPlanCfg). Free moves (cost 0) rank as cost .3 in the value/cost^alpha choice (identical for cost >= 1). Plan moves 'place' / 'fmove' are re-checked on the real board (cpuPlanOK) and executed by placeF / cpuMoveExec; a new star is addressed by its system because it has no id at plan time (cpuFleetTgt).
- Correctness: harness --check 0 mismatches (596 positions); --planchk 149 / 149 plans exact (sector counts and Actions); place fails 0, Fleet-move fails ~0.04 per game. Speed: ~45 ms per plan, same as level 4.
- Evidence (all 2p, Hard+F vs Hard+, 100 games each unless noted; Hard+F share): placement only 42%, Fleet moves only 34% (32% with fmD 0), ftake only 39%, a variant with fmA 0: 51%, final settings (fmA 0, fmD 1, ftake on, post on) 47% then 52.5% on new seeds (220 total, 50.0%). No component helped; a first Fleet-move version looked clearly worse until fmA was set to 0 (the 'a move makes a capture possible' value; ftake covers that case).
- Why (partly tested): same-position test (tools/fleetab.py: snapshots of real Hard+ turn starts, planned both ways, compares the planner's own turn value): Fleets in the plan score +5.8 (+-3.7) higher per turn over 151 positions (placement only +2.7 +-5.9, not significant), about +0.5 VP-equivalent, 2/3 of positions identical, a few large gains. So the planner does find better turns BY ITS OWN SCORE, and the immediate result is exact (planchk), yet games do not change. Not tested but likely: the gain sits in the terms the model cannot verify (retake penalty, next-turn lookahead), i.e. the evaluator rewards Fleet positions the opponent never punishes, and old cpuPlace2 / cpuFleetMove2 already capture most of the real value of Fleets in 2p. Also not modeled: Hold/Retreat choices, defending Fleets, extra Fleets the real attack adds.
- Statistics note: at 100 games per arm the win-rate error is +-9.8%; only a gap of 20 points or more is visible. A real +3% gain would need ~1,000 games, so small Fleet gains cannot be shown with this harness at a sensible cost. Same-position A/B (fleetab.py) is far cheaper for deciding between ideas than head-to-head games.
- Not done: 4p games (a Fleet pool of 3-4 for trailing players may matter more there; only worth a look if step 9 finds 4p weak).

## Tools and debugging approaches (added end of step 5)
- tools/harness.py: the self-play runner (see Working rules). tools/cmp.py REF.jsonl NEW.jsonl: compares two harness runs game by game (same seeds) and prints how many differ; use it after any change that must not alter levels 1-3 (record reference runs from the previous build first, e.g. 2p `--levels 3,2 --games 30`, `2,1 --games 20`, 4p `3,3,2,2 --games 6`). tools/prof.py HTML N LEVELS GAMES: CPU profile of a few games (self-time per function and who calls dseg/clear). tools/trace.py LEVEL SEED ROUNDS: prints the moves a 2p game makes in the first rounds, for comparing two levels on the same seed.
- To see WHY the planner chose a turn: set `cpuPlanCfg.dbg=true` (e.g. via page.evaluate) and read `cpuPS.dbg` = one row per rollout [round, rollout number, alpha, leaf value, moves as type+cost:target@value]. Equal leaf values across different plans = a tie the evaluator cannot see (this is how the missing look-ahead was found).
- Method that worked: (1) per-round VP margin instead of the final result to find WHEN a version falls behind; (2) look at raw mean VP per level per round; (3) trace one seed's early moves for both levels; (4) dump rollout values at the decision. Isolate causes with --set (evaluator terms) and --pc (planner values) before changing code.
- Approach lessons: a static end-of-turn score cannot tell apart turns that differ only in where stars end up; add a short look-ahead rather than a per-Action penalty. Check every new simulation against the real game (--planchk) before judging strength. Keep levels 1-3 byte-identical (cmp.py) when only adding a new level's code.
- tools/fleetab.py (step 6): same-position A/B. Plays games, snapshots the start of Hard+ turns, plans each snapshot twice (old Fleet code vs Fleets in the plan) and prints the average planner value of each and the paired difference (`python3 tools/fleetab.py --games 14 --reps 2 --seed0 7000 [--pc fMove=0]`, ~1-2 min). Much less noisy than head-to-head games. harness.py also has --fleet LV (let level LV plan Fleets) and prints placed / Fleet-move counts in the planner line.
- Ideas not yet tried (for steps 7-9): look-ahead that lets opponents answer (2-ply); a cheaper/better early-game opening (Hard+ trails by ~0.3 VP at rounds 6-8); tune look/thr/enable/K and the step-4 terms with 300+ games and with VP margin after round 8-10 as the main measure; scenario tests for the elimination case; time a plan on the Android before choosing K and ms.
- tools/scen.py, scen_defs.py, scendbg.py (step 9): hand-made positions. `python3 tools/scen.py run NAME --levels 3,4 --seeds 8 [--pc thr=0] [--set 3:elimPen=0]` plays one CPU turn from the position and prints own VP change, swing vs the opponent, unspent Actions and moves; `scendbg.py NAME LEVEL` prints the rollouts. Positions: elim2, elim2b, lead4. tools/ab.py FILES prints Custom(6)-vs-Hard(3) margin/win/elimination; tools/pair.py CONTROL VARIANT... gives the paired per-game difference with a 95% interval (same seeds). tools/runq.sh QUEUEFILE runs 'name|harness args' lines in order. harness.py gained `--pc6 KEY=VAL` (planner values used only by level 6), so a variant plays baseline Hard in the same games.
